PROC TENHLE BUILD EXISTUJE:
BUILD2HB ukazal, ze Wolf3D uz umi ciste logo/obrazek, ale po intru jde obraz do caje a chybi text.
V logu byl porad podezrely marker "VBXE VRAM PROBE RENDER". To byl fallback/diagnostika, ktera se po platnem XDL uz nesmi vracet a malovat pres realny VBXE obraz.
BUILD2HC proto neni kosmetika a neni to hotove VBXE. Je to stabilizacni XDL krok podle dodane dokumentace fx.pdf / vbxefx.ah.

CO JE NOVE:
1) XDL parser uklada dalsi realne stavy z XDL:
   - OVADR adresa a OVSTEP
   - OVSCRL hscroll/vscroll
   - CHBASE jako adresa fontu CHBASE * $800
   - widthSel, OV palette, PF palette, priority

2) Prvni realny TEXT XDL renderer:
   - cte text z VBXE VRAM jako dvojice znak/atribut
   - font bere z CHBASE ve VBXE VRAM
   - normalni sirka = 80 znaku, narrow = 64, wide = 84
   - text downsampluje 640px VBXE text do canvasu emulatoru 320px oblasti
   - respektuje zakladni transparentnost textoveho overlaye podle VIDEO_CONTROL no_trans/trans15

3) Graficky SR/LR/HR renderer ma upravenou transparentnost:
   - SR/LR: transparentni je 0, a pri trans15 i hodnoty $xF
   - HR: transparentni nibble 0, a pri trans15 nibble $F
   - no_trans vypina transparentnost

4) VRAM PROBE fallback je zablokovany po XDL:
   - pred XDL muze zustat jako diagnostika
   - jakmile je XDL zapnute nebo uz probehl validni XDL, probe uz nesmi kreslit caj pres obraz

5) Cold start resetuje VBXE stav:
   - registry
   - VRAM
   - XDL log/last-good stav
   - palety zpatky na default
   - tim se omezi duchove mezi testy/soubory

DULEZITE PRO DALSI KROK:
Kdyz HC ukaze TEXT XDL EMPTY, znamena to, ze parser uz text vidi, ale textova data/font nejsou na adrese, kterou zatim renderer pouziva. Pak dalsi build musi resit stavove preneseni OVADR/CHBASE mezi XDL listy nebo MAPON/MAPADR.
Kdyz HC ukaze TEXT XDL RENDER, ale text je rozsypany, dalsi build ma ladit font-line, krok OVSTEP, hscroll a atributy.
Kdyz se porad objevi "VBXE VRAM PROBE RENDER" az po validnim XDL, je to chyba a musi se opravit blokace fallbacku.
